View-only links without custody

If you hold none of the data, where does a share link come from? From a build step. The viewer is one self-contained artifact; publishing is choosing where to put it. Three places, three different tradeoffs, one piece of code.

The reframe

Publishing is a build target, not an architecture

Road 3 treated publishing as a service you run. It doesn't have to be. Build a static viewer once — an HTML bundle that reads a frozen .canvas plus its assets and renders it with pan, zoom and read-only inspection, no server, no network:

publish/<id>/
  index.html        ← the viewer, inlined
  canvas.json       ← frozen snapshot, live pages already flattened
  assets/<sha256>

Now "share" is a copy. To a bucket, to a Pages deploy, to a service — the artifact is identical every time. Every road on the map that wants a link wants this same folder, which makes it the highest-leverage thing to build in the whole exploration.

What each one really buys

  • A — their bucket. Pairs with Road 7. The client writes the bundle under a public/ prefix and hands back a signed URL. You operate nothing; expiry is a bucket policy. The catch is that most people's buckets aren't configured to serve public objects, and telling a designer to edit a CORS policy is the setup wall again, one level deeper.
  • B — Pages from the repo. Pairs with Road 8, and it's the best of the three. Publishing is a push; un-publishing is a commit; and because a commit is a version, you get something no other road on the map has: a share link pinned to an exact state, alongside a link that always shows latest. "Here's what it looked like Tuesday" is a URL.
  • C — a small service. The only one where a reviewer can leave a comment that reaches you. You take custody, but of published snapshots only — an explicit, per-artifact, deliberate act, not a product-wide posture.

The one thing you can't get for free: comments coming back

Everything else on this page works with no server. A reply channel does not — someone has to accept the write. The honest options, worst to best:

  • Reviewer exports a comments file and emails it to you. Technically zero infrastructure. Nobody will do this.
  • Comments as GitHub issues or PR comments. Free and excellent for a developer reviewer. Useless for the PM, the client, and the founder — which is most of who "can you share this?" is aimed at.
  • Host comments, not canvases. A tiny append-only service keyed by publish id. You take custody of comment threads and nothing else — a blast radius so much smaller than a workspace that it barely registers on the same scale, and it buys the entire review loop that made Road 3 worth wanting.

That split is the recommendation: the work stays theirs, the conversation about the work is yours to host. It's also the only piece of infrastructure in this whole row that you'd actually run, which keeps the ops surface to one small thing.

The viewer is where the sharp edges get contained

Road 4 flagged two hazards as multiplayer problems. They aren't — they belong to any road that moves a canvas to another machine, this one included.

Live pages must be frozen at publish. A page entity pointed at localhost:3000 renders against the reviewer's localhost — same URL, different site, no warning. Publishing has to flatten live pages to snapshots, not carry their URLs.

HTML entities must be sanitised or sandboxed. An HTML entity in a published canvas is arbitrary code running in whoever opens the link. Third-party iframe origin, CSP, no same-origin access.

Both are one-time fixes in one artifact — which is a further argument for building exactly one viewer rather than a viewer per destination.

Who does this

Excalidraw's export-to-link. Observable's static notebook exports. tldraw's static viewer. Every static-site generator's preview deploy. Figma's prototype links are the hosted version of the same idea, with custody attached.

The strategic read: the share link was never the reason to take custody — rendering server-side was, and a static bundle removes the need. What actually requires a server is the reply channel, and that's a much smaller thing to hold than someone's workspace. Publish theirs, host the conversation.
